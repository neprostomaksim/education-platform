## Основные находки

### S01 — Высокая: prototype pollution до проверки подписи платежа

**Код:** `src/app/api/prodamus/webhook/route.ts:29`, `:156`.

Парсер вложенных form-параметров проходит по обычным объектам через `cur[k]`, включая наследуемые свойства. Ключ `__proto__[audit_marker]` записывает значение в `Object.prototype`. Это происходит до проверки HMAC, поэтому даже запрос с неверной подписью меняет состояние JavaScript-контекста обработчика.

**Подтверждение:** локальный POST возвращает 403, но вновь созданный объект наследует маркер. Секрет в тесте задан. Возможны повреждение обработки последующих запросов и подмена отсутствующих свойств объектов. Полный захват процесса или универсальный обход HMAC не доказаны; такую тяжесть не заявляем.

**Исправление:** запретить `__proto__`, `constructor`, `prototype` на любой глубине; создавать словари без прототипа; проверять собственные свойства; ограничить размер тела, число параметров и глубину. После исправления перезапустить затронутые процессы, чтобы убрать уже изменённые прототипы.

### S02 — Критическая при ошибке конфигурации: бесплатная выдача оплаченного доступа

**Код:** `src/app/api/prodamus/webhook/route.ts:31`; `src/app/api/dev/simulate-purchase/route.ts:14`; `src/app/api/dev/send-claim/route.ts:15`.

При отсутствии секрета webhook продолжает обработку и сохраняет покупку как `paid`. Отсутствующий `payment_status` также считается успешной оплатой. Достаточно запроса с подходящим номером заказа и Telegram ID.

Вторая дверь — `ENABLE_TEST_PURCHASE=true`: GET без входа создаёт оплаченную покупку и возвращает ссылку активации. Проверки `NODE_ENV` или администратора нет. `send-claim` дополнительно позволяет инициировать сообщения от бота.

**Подтверждение:** оба сценария воспроизведены на mocks, тестовый GET работает и при `NODE_ENV=production`. В текущем локальном env эти ветви не активны; продакшен не проверен.

**Исправление:** при отсутствии секрета возвращать ошибку конфигурации и ничего не выдавать. Dev endpoints исключить из продакшена; в тестовом окружении требовать администратора, POST и использовать отдельные данные.

### S03 — Критическая при применении: миграция назначает всех администраторами

**Код:** `supabase/007_fix_admin_update.sql:5`.

После отключения защитного триггера выполняется `UPDATE public.profiles SET role = 'admin', is_approved = true` без WHERE. Все профили, существующие на момент выполнения, становятся администраторами, получая доступ к данным, контенту, выдаче прав и административным API.

**Условие:** миграция должна быть применена к базе с такими пользователями; вновь зарегистрированные после неё автоматически администраторами не становятся. Факт неправильных ролей в живой базе не установлен.

**Исправление:** убрать массовое назначение из процедуры развёртывания, сверить существующих администраторов с явным списком разрешённых аккаунтов, исправить роли отдельной адресной миграцией. Проверить целостность контента и выданных доступов, если лишние администраторы обнаружатся.

### S04 — Высокая: зарегистрированный пользователь может читать все профили

**Код:** `supabase/006_fix_profiles_recursion.sql:12`; `supabase/009_add_email_to_profiles.sql:6`; `supabase/028_prompts_access.sql:17`.

Политика SELECT проверяет только `auth.role() = 'authenticated'`. В таблицу позднее добавлены email и Telegram ID. Обычный аккаунт может обратиться к Supabase Data API напрямую и получить чужие профили: UUID, имя, email, роль, статусы и Telegram ID, где заполнен. Одобрение администратором не требуется этой политикой. Скрытая админская страница этому не препятствует.

**Достоверность:** подтверждено миграциями; зависит от реально применённой политики и grants. Supabase отдельно разделяет grants и ограничения строк: [документация](https://supabase.com/docs/guides/api/securing-your-api).

**Исправление:** SELECT собственного профиля плюс отдельная политика для администраторов. Для публичных имён/аватаров, если нужны, выделить безопасный набор данных без контактных и служебных полей.

### S05 — Высокая: пользователь сам меняет привязку Telegram

**Код:** `supabase/migrations/001_initial_schema.sql:89`; `supabase/007_fix_admin_update.sql:8`; `supabase/028_prompts_access.sql:21`, `:154`.

Пользователь может обновлять собственный профиль; триггер защищает только `role` и `is_approved`. `telegram_id` не защищён, хотя на нём стоит глобальный уникальный индекс и его использует выдача доступа.

**Сценарий:** аккаунт записывает в свой профиль известный Telegram ID покупателя, который ещё не привязан к профилю. Когда покупатель активирует настоящую покупку, UPDATE его профиля нарушает уникальность; откатывается вся функция, включая entitlement. Владение Telegram атакующим не проверяется. Можно занять чужую привязку и блокировать активацию. Эксплуатация внешней команды бота «Мой доступ» не проверялась — код бота отсутствует.

**Исправление:** ограничить обновляемые клиентом столбцы; Telegram-привязку менять только через проверенную серверную процедуру. Обработать конфликт привязки явно. Аналогично защитить `email`, `created_at`, `updated_at`: сейчас они также не защищены этим триггером. Изменение `profiles.email` само по себе не меняет email входа в `auth.users`.

### S06 — Высокая: платный контент и права остаются в общем кэше браузера

**Код:** `public/sw.js:55`, `:62`, `:84`; `src/hooks/use-user.ts:172`; `src/hooks/use-courses.ts:15`; `src/app/(dashboard)/lessons/[lessonId]/page.tsx:486`, `:592`; `src/components/providers/pwa-provider.tsx:34`.

Service Worker сохраняет HTML `/prompts` вместе с переданным покупателю контентом, даже если ответ имеет `Cache-Control: private, no-store`. Кэш не разделён по аккаунтам, выход удаляет только локальные user/profile. Курсы, тексты уроков, прогресс и другие кэши остаются. Страница урока восстанавливает контент из кэша не только без сети, но и после ошибки/отказа БД, обходя последующую проверку доступа.

**Подтверждение:** mock Service Worker выдал второму пользователю платный HTML первого пользователя при отсутствии сети. Это утечка в одном профиле браузера, а не доступ из любого браузера в интернете. Отзыв прав не убирает ранее сохранённые материалы.

**Исправление:** не кэшировать платный HTML, RSC/Flight-ответы и auth/claim страницы; соблюдать запреты кэширования. Изолировать локальные данные по user ID и очищать все приватные кэши при выходе/смене пользователя. Не подменять 401/403/отказ RLS офлайн-успехом. Решение об офлайн-доступе после отзыва права должно быть явным; уже скачанный контент технически нельзя «забрать» у пользователя.

### S07 — Высокая, эксплуатация зависит от формы оплаты: нет проверки ожидаемого заказа

**Код:** `src/app/api/prodamus/webhook/route.ts:48`, `:68`, `:70`, `:89`.

Любое подписанное уведомление с номером `prompts_<tg>_<...>` выдаёт продукт `prompts`. Нет сравнения с созданным сервером заказом, ожидаемой ценой, валютой, составом корзины и доменом платёжной формы. Сумма преобразуется `parseInt`, поэтому копейки теряются. Отсутствующий статус принят за успех. В `provider_order_id` записывается прежде всего `order_num`, хотя это номер магазина, а не ID операции провайдера. Различие описано у [Prodamus](https://help.prodamus.ru/payform/uvedomleniya/kak-ustroena-otpravka-uvedomlenii-ob-oplate).

**Подтверждение:** локальное корректно подписанное тестовым ключом уведомление с `sum=0.01`, `currency=USD` и без статуса создало `paid`, amount=0. Это доказывает отсутствие проверок, но не возможность подделать подпись реального провайдера. Покупка за меньшую сумму в продакшене зависит от возможности менять параметры платёжной формы/ссылки; генератор ссылок бота отсутствует в репозитории.

**Исправление:** серверный pending order с фиксированными продуктом/ценой/валютой/получателем; строгая сверка webhook; сумма в минимальных денежных единицах; требовать явный успешный статус; уникальность по `(provider, provider transaction id)`, номер магазина хранить отдельно.

### S08 — Высокая при пропуске заголовков прокси: одноразовый токен уходит на чужой домен

**Код:** `src/app/api/prodamus/webhook/route.ts:235`; `src/app/api/dev/send-claim/route.ts:64`.

URL активации строится из `x-forwarded-host`/`host` прежде заданного `NEXT_PUBLIC_APP_URL`. Эти заголовки не покрывает HMAC тела. Если инфраструктура допускает контролируемый forwarded host и атакующий может вызвать принимаемый webhook, бот отправит пользователю ссылку на чужой домен с действительным claim-токеном. После перехода владелец домена может активировать покупку на своём аккаунте.

**Подтверждение:** при заданном корректном APP_URL тестовый подписанный webhook отправил ссылку на `collector.example`. Прохождение подменённого заголовка через реальный ingress не проверено.

**Исправление:** использовать доверенный origin из серверной конфигурации, валидировать его при запуске, запретить произвольные Host/Forwarded значения на входе.

### S09 — Средняя: открытые перенаправления после авторизации

**Код:** `src/app/(auth)/login/page.tsx:36`; `src/app/(auth)/register/page.tsx:51`; `src/app/(auth)/callback/route.ts:7`.

`startsWith('/')` пропускает `//collector.example/` и некоторые формы с обратными слешами. В callback значение вообще конкатенируется с origin без проверки: `next=@collector.example/` создаёт URL, где исходный домен становится userinfo, а назначение — чужой сервер.

**Подтверждение:** URL-разбор и callback с подставным успешным обменом кода воспроизвели выход на чужой домен. Для callback требуется успешный auth code; для регистрации — созданная сессия. Это фишинговый redirect, не доказанная утечка сессионных cookies.

**Исправление:** единая функция нормализации относительного пути с проверкой `new URL(value, trustedOrigin).origin`, запретом credentials, `//`, обратных слешей и управляющих символов. Разрешить только необходимые внутренние назначения.

### S10 — Средняя: возврат оплаты не отзывает доступ, повторы меняют платёжное состояние

**Код:** `src/app/api/prodamus/webhook/route.ts:76`, `:83`, `:106`; `src/lib/entitlements.ts:25`; `supabase/028_prompts_access.sql:130`.

В репозитории нет обработки возврата с отзывом entitlement. Проверка доступа читает entitlement и не читает статус покупки. Повторное уведомление успеха снова пишет `status=paid` и отправляет сообщение. Поэтому ручная смена покупки на refunded сама по себе не закрывает промпты, а старое успешное уведомление может затереть refunded. Блокировка строки в claim защищает одновременную активацию, но не исправляет эту модель событий.

**Подтверждение:** искусственное подписанное событие с `payment_status=refunded` игнорируется; повторное success повторяет отправку. Реальный формат событий возврата Prodamus отдельно не подтверждён; вывод об отсутствии механизма отзыва основан на поиске по всему приложению.

**Исправление:** явные переходы платёжного состояния, журнал событий, обработка возвратов и спорных платежей согласно возможностям провайдера. Идемпотентная выдача/отзыв прав и отправка сообщений; учитывать другие действующие покупки того же продукта. Сохранять tombstone возврата, запрещающий старому success восстановить оплату.

### S11 — Средняя, если материалы должны быть платными: файлы доступны без покупки

**Код:** `public/lesson-files/`; `supabase/017_lesson_images_storage.sql:7`; `src/lib/supabase/middleware.ts:47`.

Раздаточные материалы размещены в публичной директории Next.js, скриншоты — в публичном bucket. Прямая ссылка работает независимо от права на урок. Часть имён файлов очевидна, ссылки можно передавать дальше. Это подтверждённая архитектура выдачи, но нарушение бизнес-требования только если эти файлы должны быть закрытыми. Пользовательские пароли или реальные персональные данные в этих учебных файлах этим аудитом не установлены.

**Исправление:** приватный bucket и выдача короткоживущих ссылок после проверки курса/урока. Явно публичные образцы можно оставить доступными.

Не запускать `npm audit fix --force` вслепую. Для build-time библиотек отдельно оценить, принимает ли сборка недоверенные CSS/YAML/glob-входы; текущих публичных endpoints для этого не обнаружено.

## Дополнительные замечания и ограничения

- **Доставка покупки теряется при ошибке Telegram.** `sendClaimLink` не проверяет HTTP status/`ok`, ловит исключение и всё равно приводит к webhook 200. Локально ответ Telegram 429 сопровождался webhook 200. Это подтверждённый дефект надёжности платёжной воронки, а не самостоятельный обход доступа. Нужен outbox с повторными попытками и статусом доставки.
- **Автоматическая активация на посещении `/claim`.** Токен является bearer-секретом: кто первым открыл ссылку с активной сессией, тому достаётся покупка. Возможны случайная активация не того аккаунта и нежелательная Telegram-привязка при переходе по чужой ссылке. Нет подтверждения выбранного аккаунта/Telegram. Само отсутствие отдельного Telegram Login не доказывает дыру в модели bearer-активации. Токен остаётся в URL, истории и общем SW-кэше; после обработки его следует убирать, auth/claim страницы не кэшировать и редактировать query-параметры в логах.
- **Широкий UPDATE профиля затрагивает миграцию 029.** При разрешённом изменении `created_at` одобренный пользователь может поставить дату до отсечки. Если 029 повторно запустят, он получит grandfather entitlement. Нужны неизменяемые служебные поля и фиксированный список/журнал миграции. Это условный сценарий, не немедленная бесплатная покупка.
- **Rate limits / CAPTCHA / MFA не подтверждены.** В приложении нет собственных ограничителей webhook/claim, CAPTCHA-потока и MFA-проверки для админских операций. Supabase имеет собственные настройки защиты; без их чтения нельзя утверждать, что brute force не ограничен или email confirmation отключён. Клиентский минимум 6 символов не заменяет серверную password policy. Генератор админских паролей использует `Math.random()` (`admin/users/page.tsx:145`), лучше `crypto.getRandomValues()` либо приглашение со сменой пароля.
- **Файлы и HTML.** Upload требует подтверждённого администратора и ограничивает MIME/размер, но не проверяет сигнатуру/декодирование содержимого. Сырой `rehype-raw` присутствует в package.json, однако в текущем рендере уроков не подключён. `dangerouslySetInnerHTML` не найден. Подтверждённый stored XSS через Markdown не заявляется. `video_url` попадает в iframe без allowlist/sandbox; источник редактируется админом. Mermaid-схемы отправляются во внешний mermaid.ink — учитывать конфиденциальность контента.
- **Заголовки.** В next.config.ts не заданы CSP/frame-ancestors и другие дополнительные заголовки. Фактические заголовки CDN/хостинга не проверены. Отсутствие настройки в файле само по себе не доказывает успешный clickjacking или CSRF. API с cookie-auth стоит дополнить проверкой Origin/Fetch Metadata; не объявляем универсальный CSRF без проверки cookie SameSite и браузерного сценария.
- **Маршрут курса.** `/courses` отсутствует в `isProtectedRoute`; оболочка не блокирует отсутствие `user`. При действующем RLS это не доказывает чтение чужой базы, но в сочетании с общим локальным кэшем ухудшает изоляцию. Проверять пользователя на сервере во всех закрытых маршрутах.
- **Админские API.** Проверяют `auth.getUser()` и роль в БД до использования service role; обход простой подменой `localStorage.role` не подтверждается. Однако часть UI доверяет кэшированному профилю: это может показать неверный интерфейс, не равно серверному админ-доступу. Создание auth user и обновление профиля не атомарны; при ошибке остаётся частично созданный аккаунт. В логах много имён/email и вычисленные HMAC при несовпадении; сократить чувствительное логирование.
- **Функции БД.** Claim использует `FOR UPDATE`, срок жизни, статусы, повторную активацию тем же пользователем и REVOKE для PUBLIC/anon/authenticated — это полезные защиты. Нужен явный контроль EXECUTE для service_role: при иных default privileges он может быть утрачен; это дефект доступности, не доказанная публичность RPC. Триггерные SECURITY DEFINER-функции `handle_new_user`/`check_profile_update` не закрепляют search_path, но используют квалифицированные таблицы/функции; рабочая цепочка повышения прав не найдена.
