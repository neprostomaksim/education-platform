## Что изменилось

- Prodamus: обязательная подпись HMAC по официальному формату, безопасный ограниченный разбор form-data, проверка успешного статуса, формы, суммы 490 RUB, количества и цены товара. Идентификатор транзакции провайдера хранится отдельно от `order_num`; повторные уведомления обрабатываются идемпотентно. Без секретного ключа обработчик возвращает 503, доступ не выдаётся. Тестовые покупки отключены безусловно.
- Активация: доверенный origin, серверная сессия, защита от cross-origin запросов, лимит попыток, атомарная одноразовая привязка покупки, проверка конфликта Telegram. Перед привязкой покупатель подтверждает показанный аккаунт. `next` сохраняется при переходах между входом и регистрацией и не допускает внешний редирект.
- Доставка: ошибки Telegram возвращают 503 для повтора провайдером; конкурентные доставки ограничены блокировкой в БД. Администратор может повторить неудачную доставку или обновить истёкшую неактивированную ссылку. Возможна повторная доставка при сбое между отправкой Telegram и фиксацией результата в БД; покупка при этом остаётся одной.
- Возвраты: в `/admin/purchases` отмечается возврат, уже выполненный в Prodamus. Это отзывает доступ от покупки, сохраняя другие действующие покупки и бессрочные ручные выдачи. Повторное успешное уведомление не отменяет возврат. Автоматический webhook возврата не заявляется: его контракт не подтверждён.
- Профили: RLS ограничивает чтение своим профилем/администратором; клиент не может менять Telegram, email, дату создания и ID. Роль/одобрение защищены триггером. Массовое повышение всех пользователей удалено из старого файла 007; уже назначенные роли новая миграция не меняет.
- Закрытые страницы/API проверяют аккаунт на сервере. Статические вложения перенесены в `private/lesson-files` и выдаются после проверки доступа к ссылающемуся уроку. Bucket изображений становится приватным; старые URL преобразуются при отображении. Загрузка изображений доступна администратору, проверяет размер/тип/пиксели и перекодирует изображения в WebP.
- Платный контент, профили и прогресс больше не сохраняются в общих постоянных кешах. Старые LMS-кеши удаляются. Офлайн-доступ к урокам и очередь офлайн-прогресса отключены; старые несинхронизированные отметки не переносятся. Новые ответы вложений имеют `private, no-store`. Уже скачанные материалы отозвать невозможно.
- Next.js обновлён до 16.3.4, Sharp до 0.35.0, совместимые транзитивные зависимости обновлены. Оптимизатор изображений Next отключён. Добавлены защитные HTTP-заголовки; CSP ограничивает embedding, objects, base и формы, но не является полной политикой защиты от XSS.

## Применение

1. Сохранить резервную копию БД. Запустить `scripts/security-audit-readonly.sql` в SQL Editor рабочей Supabase и проверить фактические политики/роли. Особенно важно сверить настоящих администраторов: старая 007 могла повысить всех пользователей. Список подтверждён 7 сентября, текущее состояние ему соответствует; понижение ролей не требуется. Проверить старые Telegram-привязки и ручные/grandfather-доступы; новая миграция не устанавливает их достоверность задним числом.
2. Подготовить релиз и переменные Vercel ниже. Миграция `supabase/030_security_hardening.sql` уже применена владельцем после 029; следующий шаг — развернуть новый код. Не запускать повторно все старые SQL-файлы: среди них есть первоначальные назначения доступов и создание публичного bucket. До нового кода старые изображения могут временно перестать открываться; до 030 новые API платежей/лимитов возвращают ошибки. При необходимости повторной доставки использовать уведомления Prodamus и `/admin/purchases` после релиза.
3. Развернуть весь проект, включая `private/lesson-files` и новый `public/sw.js`. Next tracing включает приватные вложения в серверную функцию. Старые deployment URL Vercel со старым кодом нужно закрыть средствами доступа/удалением ненужных deployments: обновление основного домена их не исправляет. Ранее публичные изображения могли остаться в CDN-кешах; проверить старые ссылки и очистить кеши доступными средствами провайдера.
4. В Supabase Auth установить серверную минимальную длину пароля 12, подтверждение email и подходящие лимиты регистрации/входа. Локальный код проверяет длину, но публичный Auth API можно вызвать напрямую — серверные настройки обязательны. Проверить Site URL и allowlist callback для точного рабочего origin, без широких wildcard. Эти настройки в рабочем проекте ещё не проверены/не изменены.
5. После релиза проверить на отдельных тестовых аккаунтах: отсутствие доступа до оплаты, настоящий платёж 490 RUB, получение ссылки, вход/регистрацию и подтверждение, повтор вебхука без повторной покупки, отказ другой учётной записи, права на уроки/вложения, возврат. Проверить фактические поля подписанного уведомления своей формы до открытия продаж. Локальные фикстуры не заменяют такую интеграционную проверку.

### Переменные окружения

```dotenv
APP_URL=https://education-platform-chi-peach.vercel.app
PRODAMUS_DOMAIN=dimablok.payform.ru
PROMPTS_PRICE_RUB=490
```

Эти значения уже используются как production defaults; явная конфигурация облегчает проверку. Рабочий URL промптов — `/prompts`, активации — `/claim?token=<одноразовый UUID>`. 990 — рекламная прежняя цена, проверяется фактически оплаченная сумма 490. Если форма не присылает `currency`, RUB определяется закреплённой формой; она должна принимать именно рубли.

Также обязательны существующие `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `PRODAMUS_SECRET_KEY`, `TELEGRAM_BOT_TOKEN`. Секреты задаются только на сервере. Дополнительно можно задать `PRODAMUS_PROMPTS_PRODUCT_NAME` ровно как в подписанном уведомлении для проверки названия товара. Без него проверяются подписанный `prompts_<telegram_id>_<id>`, одна позиция, количество и цена; отдельного реестра заказов бота в этом репозитории нет. Секреты не помещать в Git. Удалить устаревшую `ENABLE_TEST_PURCHASE`.

Для preview нужна отдельная тестовая конфигурация с точным `APP_URL`; production origin намеренно не разрешает изменения с произвольных preview-доменов.

## Проверки

Финальный результат: 18/18 тестов Node пройдены, SQL assertions пройдены, TypeScript и production-сборка Webpack пройдены; npm audit — 0 известных уязвимостей. Все 26 вложений побайтово совпадают с исходными и включены в серверный build trace. В изменённых файлах остаются 8 прежних ESLint-ошибок в страницах пользователей/урока; новые модули не имеют ошибок ESLint.

```sh
npm run test:security
npx tsc --noEmit
npm run build -- --webpack
```

Тесты используют подставные БД/Telegram, проверяют отказ без подписи, prototype pollution, лимиты парсера, сумму/валюту/форму, формат подписи со слешами, повторы/сбои доставки, отключённые тестовые маршруты, CSRF/сессию/лимиты активации, запрет админских операций студенту и приватность SW. Проверки PostgreSQL используют настоящий локальный PostgreSQL с упрощёнными заглушками `auth`/`storage`: это проверка SQL и RLS, а не полного Supabase Auth/Storage.

Для SQL-тестов создать отдельный пустой локальный кластер. **Никогда не направлять bootstrap в рабочую БД**: он создаёт служебные роли, схемы и фикстуры.

```sh
psql -v ON_ERROR_STOP=1 -d <пустая_локальная_БД> -f scripts/security-tests/bootstrap.sql
psql -v ON_ERROR_STOP=1 -d <локальная_БД> -f scripts/security-tests/assertions.sql
```

Bootstrap проверяет повторное применение 030. Assertions проверяет профили/RPC ACL, платежи, блокировку доставки, обновление истёкшей ссылки, одноразовую активацию/Telegram-конфликт, отзыв после возврата и лимиты; данные откатываются. Turbopack в текущей среде не смог открыть служебный порт; production-сборка проверяется через поддерживаемый Webpack. Полный ESLint проекта имеет прежние ошибки, не связанные с этим исправлением; он не заявляется пройденным.
